# VeyRA — Technical Design Specification

## Version 0.2 — Implementation-Oriented Architecture

---

# 0. Executive Definition

## Product Name

**Veyra**

## Product Definition

> **Veyra is an AI operating layer for Windows that turns human intent into verified execution.**

Veyraは、単なる音声入力ソフトでも、ChatGPTクライアントでも、Windows用Siriでもない。

Veyraの役割は、

```text
Human Intent
    ↓
Goal
    ↓
Context
    ↓
AI Selection
    ↓
Planning
    ↓
Execution
    ↓
Verification
    ↓
State Update
    ↓
Human
```

を一つのRuntimeとして提供することである。

ユーザーは「AIをどう使うか」を考えなくてよい。

ユーザーは、

> 「これを作って」
> 「ここ違う」
> 「もっとこうして」
> 「完成するまでやって」

と要求する。

Veyraはその要求を長期Goalとして保持し、その時点で最適なAI・Toolを利用してタスクを進める。

---

# 1. Core Principles

Veyraは以下の原則を設計上の不変条件とする。

## 1.1 Conversation Context ≠ Goal

会話履歴は一時的なContextである。

Goalは永続的なプロジェクト状態である。

```text
Conversation
    └── temporary context

Goal
    ├── objective
    ├── requirements
    ├── constraints
    ├── acceptance criteria
    └── decisions
```

Context compressionによって会話が要約・削除されても、Goalが失われてはならない。

---

## 1.2 Goal ≠ Project State

Goalは「何を達成するか」。

Stateは「現在どうなっているか」。

```text
Goal:
    Build a Windows AI assistant.

State:
    Voice pipeline complete.
    Calendar integration incomplete.
    12 tests passing.
```

GoalをStateに混ぜない。

---

## 1.3 Event Log = Historical Source of Truth

状態を直接上書きするのではなく、重要な変更をEventとして記録する。

```text
User feedback
Goal update
Tool execution
File modification
Verification
Decision
```

Current StateはEvent Logから再構築可能な設計にする。

---

## 1.4 LLM ≠ Runtime

LLMは知能エンジン。

Veyra Runtimeは、その知能を使うためのOS層。

```text
Veyra Runtime
    ↓
GPT / Claude / Codex / Hermes / Local LLM
```

特定モデルへの依存を避ける。

---

## 1.5 Generate ≠ Done

AIが

> "Completed successfully."

と言ったことを完了条件にしない。

必ず、

```text
Execute
    ↓
Verify
    ↓
Update State
```

を通す。

---

## 1.6 Voice ≠ Product

VoiceはVeyraへの最も自然なInputの一つ。

本体は、

> **Intent → Goal → AI → Tools → Verification**

である。

---

# 2. What Veyra Actually Does

Veyraは大きく6つの仕事を持つ。

```text
1. Understand
2. Remember
3. Decide
4. Execute
5. Verify
6. Continue
```

### Understand

ユーザーの発話・入力をIntentへ変換する。

### Remember

Goal、Decision、Feedback、Project Stateを保持する。

### Decide

どのAI・Toolを利用すべきか判断する。

### Execute

AIに仕事をさせ、Windowsや外部サービスを操作する。

### Verify

生成物がGoalを満たしているか検証する。

### Continue

ユーザーからの修正指示を元に、既存Goalを維持したまま作業を継続する。

# 7. Voice System

## 7.1 Voice Modes

Veyra has two fundamentally different Voice Modes.

### Flow Mode

Purpose:

> **Fast text entry**

Pipeline:

```text
Microphone
    ↓
VAD
    ↓
Streaming STT
    ↓
Sentence boundary
    ↓
Local cleanup
    ↓
Text injection
```

No full Agent loop.

No complex planning.

No unnecessary cloud calls.

---

### Assistant Mode

Purpose:

> **Execute an instruction**

Pipeline:

```text
Microphone
    ↓
STT
    ↓
Intent Detection
    ↓
Goal Resolution
    ↓
Context Builder
    ↓
Agent
    ↓
Tools
    ↓
Verification
```

---

# 8. Voice Latency Model

Veyra must not wait for full recording completion before showing feedback.

```text
Audio
 ↓
chunk 1 ──→ STT partial
chunk 2 ──→ STT partial
chunk 3 ──→ STT partial
```

The UI should display live transcription.

However, the active application should receive only the final normalized text by default.

This avoids destructive replacement races.

---

# 9. Natural Language Cleanup

Flow Mode requires a specialized lightweight transformation step.

Input:

> "えーっと今日のミーティングなんですけどまぁ来週までには終わらせたいと思っていて"

Output:

> "今日のミーティングについてですが、来週までには終わらせたいと考えています。"

Rules:

```text
Remove fillers
Remove accidental repetition
Preserve meaning
Preserve technical terms
Do not invent information
Do not answer the user
Do not summarize unless requested
Do not alter intent
```

This component should preferably be local and low-latency.

# 10. Goal Engine

Goal is the most important persistent object in Veyra.

## Goal structure

```rust
struct Goal {
    id: GoalId,
    project_id: ProjectId,

    objective: String,

    requirements: Vec<Requirement>,
    constraints: Vec<Constraint>,
    preferences: Vec<Preference>,

    acceptance_criteria: Vec<AcceptanceCriterion>,

    status: GoalStatus,

    created_at: DateTime<Utc>,
    updated_at: DateTime<Utc>,
}
```

# 11. Requirements

Requirements are explicit statements of what must exist.

Example:

```text
REQ-001
Application must run on Windows 11.

REQ-002
Voice input must work from any active application.

REQ-003
User must be able to interrupt a running task.
```

Requirement state:

```text
unknown
planned
in_progress
verified
failed
waived
```

---

# 12. Acceptance Criteria

Acceptance Criteria define when Veyra may say:

> "Done."

Example:

```text
AC-001
Application launches without error.

AC-002
Push-to-talk activates within target latency.

AC-003
Voice input is inserted into the foreground application.

AC-004
All core tests pass.
```

Without satisfied Acceptance Criteria:

```text
Goal.status != completed
```


# 14. Decision Store

Important decisions should survive context compression.

Example:

```text

```

Decision is not just chat history.

# 15. Event Log

Every meaningful state transition produces an Event.

```rust

    event_type: EventType,
    payload: JsonValue,

    created_at: DateTime<Utc>,
}
```

Examples:

```text

tool_requested
tool_started
tool_completed
tool_failed

```

---

# 16. Event Immutability

Event Log entries are append-only.

Do not edit historical events.

Correction:

```text
Bad:
Modify old event

Good:
Append corrective event
```

Example:

```text
goal requirement changed
```

becomes:

```text
goal_updated
{
    "old": "...",
    "new": "..."
}
```

---

# 17. Current State Projection

Current state is a materialized projection of historical events.

```text
Event Log
   ↓
Projector
   ↓
Goals
Project State
Decisions
Issues
```

This allows Veyra to reconstruct state after a crash or database recovery.

# 18. Context Engine

The Context Engine determines what an AI should see.

Never send the entire project history blindly.

Context Package:

```rust
struct ContextPackage {
    goal: Goal,
    project_state: ProjectState,

    relevant_requirements: Vec<Requirement>,
    relevant_decisions: Vec<Decision>,
    relevant_feedback: Vec<Feedback>,

    active_application: Option<ApplicationContext>,

    relevant_files: Vec<FileContext>,

    recent_events: Vec<Event>,

    current_user_request: InputEvent,
}
```

---

# 19. Context Priority

When context is limited:

```text
Priority 1
Current user request

Priority 2
Active Goal

Priority 3
Relevant Acceptance Criteria

Priority 4
Current Project State

Priority 5
Relevant Decisions

Priority 6
Relevant User Feedback

Priority 7
Relevant recent events

Priority 8
Older conversation
```

Conversation history is the lowest-value context.

Structured project state is more important.

# 20. AI Gateway

All models communicate through a provider interface.

```rust
trait AIProvider {
    fn id(&self) -> ProviderId;

    fn capabilities(&self) -> Capabilities;

    async fn complete(
        &self,
        request: AIRequest
    ) -> Result<AIResponse>;

    async fn stream(
        &self,
        request: AIRequest
    ) -> Result<AIStream>;
}
```

This prevents the Runtime from knowing model-specific APIs.

# 26. UI Interaction Capability Layer

Agent should not care whether interaction is performed by UIA, OCR, or Vision.

Expose:

```text
read(target)
click(target)
type(target, text)
select(target)
```

Internal resolver:

```text
UIA
 ↓
OCR
 ↓
Vision
```

This makes the Agent interface stable even when the underlying automation mechanism changes.

---

# 27. Windows UI Resolution

Resolution order:

```text
1. Accessibility/UI Automation
2. Native application APIs
3. Clipboard
4. OCR
5. Vision
```

Do not use Vision if a deterministic API exists.

Vision is the fallback, not the default.

---

# 28. File Drift Detection

Veyra must assume that files can be changed outside Veyra.

Examples:

```text
User edits file in VS Code
Git checkout changes files
External process modifies file
AI modifies file outside Veyra
```

Therefore the Runtime monitors project directories.

```text
Filesystem Watcher
      ↓
Changed File
      ↓
Hash / metadata check
      ↓
Reconciler
      ↓
Event Log
      ↓
Project State update
```

The internal state must never blindly assume that the filesystem matches the last AI action.

---

# 29. File Identity

File state should include:

```text
path
size
modified_time
content_hash
```

For important files:

```text
SHA-256
```

or another stable content hash.

This allows Veyra to distinguish:

```text
expected modification
```

from

```text
external modification
```

Prefer deterministic verification.

```text

    ↓

    ↓
```

# 33. User Feedback Loop

The following interaction must be a first-class use case:

> 「ここ違う」

Veyra must resolve "ここ" using current context.

It creates:

```text
Feedback Event
```

Then builds:

```text
Goal
+
Relevant Requirement
+
Current State
+
Latest Artifact
+
User Feedback
```

This becomes the review context.

The AI is not allowed to rely solely on the immediately previous response.

---

# 34. Goal Drift Detection

When the new user request conflicts with the original Goal:

```text
Original Goal
      +
New Feedback
      ↓
Consistency Check
```

Example:

Original:

> Dark minimal interface

New:

> 「もっと派手でカラフルに」

Veyra should not silently overwrite the original requirement.

Instead:

```text
Goal conflict detected.

Original preference:
Dark minimal

New feedback:
Colorful visual treatment

Resolution required:
Which requirement should take precedence?
```

For low-risk changes, Veyra may update the Goal automatically and append a decision event.

---

# 35. Goal Evolution

Goal is persistent, but not immutable.

Important distinction:

```text
Goal is durable
≠
Goal cannot change
```

Goal updates must be explicit events.

```text
goal_updated
```

This preserves history.

---

# 36. Session Architecture

Session is temporary.

```text
Session
 ├── messages
 ├── current request
 ├── temporary context
 └── active tool execution
```

Ending a session does not end a Goal.

```text
Session ends
     ↓
Goal remains
     ↓
Project remains
```

This is critical.

---

# 37. Memory Architecture

Veyra uses layered memory.

```text
L0 — Input
Current utterance

L1 — Session
Current conversation

L2 — Project
Current project state

L3 — Goal
Persistent objective / requirements

L4 — Decisions
Important decisions

L5 — User Preferences
Stable preferences
```

Each layer has a different lifecycle.

# 38. SQLite Schema

Core schema:

```sql
CREATE TABLE projects (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    root_path TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE goals (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    objective TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(project_id) REFERENCES projects(id)
);

CREATE TABLE requirements (
    id TEXT PRIMARY KEY,
    goal_id TEXT NOT NULL,
    type TEXT NOT NULL,
    content TEXT NOT NULL,
    status TEXT NOT NULL,
    FOREIGN KEY(goal_id) REFERENCES goals(id)
);

CREATE TABLE acceptance_criteria (
    id TEXT PRIMARY KEY,
    goal_id TEXT NOT NULL,
    content TEXT NOT NULL,
    status TEXT NOT NULL,
    FOREIGN KEY(goal_id) REFERENCES goals(id)
);

CREATE TABLE project_states (
    project_id TEXT PRIMARY KEY,
    current_phase TEXT,
    current_task TEXT,
    last_verified_at TEXT,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(project_id) REFERENCES projects(id)
);

CREATE TABLE decisions (
    id TEXT PRIMARY KEY,
    project_id TEXT NOT NULL,
    decision TEXT NOT NULL,
    rationale TEXT,
    created_at TEXT NOT NULL,
    FOREIGN KEY(project_id) REFERENCES projects(id)
);

CREATE TABLE event_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id TEXT NOT NULL,
    session_id TEXT,
    event_type TEXT NOT NULL,
    payload JSON NOT NULL,
    created_at TEXT NOT NULL,
    FOREIGN KEY(project_id) REFERENCES projects(id)
);
```

# 43. Interrupt System

Veyra must support:

```text
Pause
Cancel
Replan

```

Example:

> 「いや待って、それ違う」

This should be interpreted as an interruption signal when an Agent is active.

---

# 44. Rollback

Rollback does not mean blindly undoing everything.

Veyra should record:

```text
Files modified
Processes launched
Tools executed
Events generated
```

Then generate a reversible action plan.

High-risk rollback requires confirmation.

# 45. Permissions

Every Tool call receives a permission level.

```text
READ
LOW_RISK
MEDIUM_RISK
HIGH_RISK
CRITICAL
```

Examples:

```text
Read file → READ
Create file → LOW_RISK

Modify source → MEDIUM_RISK
Delete files → HIGH_RISK
```

# 64. Final Product Definition

**Veyra does not attempt to become the smartest AI.**

Veyra attempts to become the **best system for using smart AI**.

The user should not need to know:

```text
Which model?
Which prompt?
Which tool?
Which context?
Which API?
Which workflow?
```

The user only needs to communicate:

```text
What do I want?
What is wrong?
What should change?
Is it done?
```

Veyra handles the rest.

---

# 65. Development North Star

Every new Veyra feature should answer one question:

> **"Does this reduce the distance between what the human wants and what the AI can successfully accomplish?"**

If yes, it belongs in Veyra.

If it merely makes Veyra look like a more impressive chatbot, it does not.
